# Branch-Native SubAgents Proposal

**Document:** `02.1.9 Branch-Native SubAgents Proposal.md`  
**Version:** 1.0.0  
**Date:** May 2026  
**Status:** Proposal  
**Supersedes:** `SubAgentSessionMode` as the primary subagent execution model  
**Depends On:** session/branch split, branch metadata, `IAgentStore`, `StoredAgent`, `AgentBuilder.WithAgentId`, `FunctionExecutionContext.SessionId`, `FunctionExecutionContext.BranchId`, parent session store access  
**Required By:** durable subagent workspaces, inspectable subagent execution, branch-native HPD-OS UI, stored-agent subagent references

## Executive Summary

HPD-Agent subagents should become branch-native.

The current subagent model treats session mode as the main execution choice:

```text
Stateless
SharedSession
PerSession
```

That was reasonable when a session still behaved like a conversation thread. It is no longer the right abstraction after the session/branch split.

The current architecture now means:

```text
Session = shared workspace/container
Branch  = conversation and execution history
```

Therefore subagent invocation should answer three separate questions:

```text
1. Which agent definition runs?
2. Which session/workspace owns the run?
3. Which branch receives the subagent's work?
```

The recommended default is:

```text
ParentSession + ForkFromParentBranch
```

That means a subagent runs inside the caller's session, forks a new branch from the caller's branch, writes its full work into that subagent branch, and returns only the tool result to the parent branch.

This keeps parent conversations clean while making subagent work durable, inspectable, replayable, and attributable.

Because backward compatibility is not required, this should be implemented as a breaking semantic replacement instead of a retrofit.

## Problem

The current subagent API uses `SubAgentSessionMode`:

```csharp
public enum SubAgentSessionMode
{
    Stateless,
    SharedSession,
    PerSession
}
```

This enum mixes concerns that are now separate:

- agent identity;
- session/workspace ownership;
- branch context;
- branch write target;
- subagent memory/lifetime.

The mismatch is most visible in `PerSession`.

The code comments describe `PerSession` as read-only parent context inheritance. In practice, the generated subagent wrapper attaches the parent session store and runs the child agent with the parent `SessionId` and parent `BranchId`.

Current effective behavior:

```text
PerSession subagent
    uses parent session
    uses parent branch
    reads parent branch history
    writes child user/assistant messages into parent branch
```

That is not read-only. It is parent-branch participation.

This matters because branches are now first-class execution lanes. A subagent should be able to work in a distinct branch inside the same session.

## Current Code Shape

### SubAgent Definition

Today `SubAgent` embeds an inline `AgentConfig`:

```csharp
public class SubAgent
{
    public string Name { get; internal set; }
    public string Description { get; internal set; }
    public AgentConfig AgentConfig { get; internal set; }
    public SubAgentSessionMode SessionMode { get; internal set; }
    public string? SharedSessionId { get; set; }
    public string? SharedBranchId { get; set; }
    public Type[] ToolHarnessTypes { get; set; }
}
```

This means a subagent definition currently carries the child agent recipe inline.

### Generated SubAgent Wrapper

The source generator builds a child agent from that inline config:

```csharp
var agentBuilder = new AgentBuilder(subAgentDef.AgentConfig);
```

It then optionally inherits the parent chat client:

```csharp
if (subAgentDef.AgentConfig.Provider == null && parentChatClient != null)
{
    agentBuilder.WithChatClient(parentChatClient);
}
```

For `PerSession`, it attaches the parent session store before building:

```csharp
var parentStore = functionContext?.GetParentSessionStore();
if (parentStore != null)
    agentBuilder.WithSessionStore(parentStore);
```

Then it runs with the parent route:

```csharp
await agent.RunAsync(new UserTextInputEvent(query)
{
    SessionId = parentSessionId,
    BranchId = parentBranchId
}, cancellationToken);
```

That is the old behavior that should be broken.

### Agent Store Foundation

HPD-Agent already has the foundation for stable agent identities:

```csharp
public class StoredAgent
{
    public string Id { get; init; }
    public string Name { get; set; }
    public AgentConfig Config { get; set; }
    public DateTime CreatedAt { get; init; }
    public DateTime UpdatedAt { get; set; }
    public Dictionary<string, object>? Metadata { get; set; }
}
```

And:

```csharp
public interface IAgentStore
{
    Task<StoredAgent?> LoadAsync(string agentId, CancellationToken ct = default);
    Task SaveAsync(StoredAgent agent, CancellationToken ct = default);
    Task DeleteAsync(string agentId, CancellationToken ct = default);
    Task<List<string>> ListIdsAsync(CancellationToken ct = default);
}
```

`AgentBuilder` already supports:

```csharp
builder.WithAgentId(agentId);
builder.WithAgentStore(store);
```

That makes stored-agent subagents natural.

### Session/Branch Foundation

The current session model is:

```text
Session
    metadata
    session-scoped middleware state
    assets/content
    shared store reference

Branch
    messages
    branch metadata
    branch-scoped middleware state
    branch events
    execution history
```

`Agent.CreateSessionAsync` creates a session with a default `main` branch.

`Agent.ForkBranchAsync` already supports branch metadata:

```csharp
await agent.ForkBranchAsync(
    sessionId,
    sourceBranchId,
    newBranchId,
    fromMessageIndex,
    metadata,
    cancellationToken);
```

That is the right primitive for subagent branches.

## Target Model

A subagent should be defined by:

```text
SubAgent
    identity shown to parent LLM
    agent source
    session policy
    branch policy
    toolharness/tool additions
    metadata defaults
```

The core invariant:

```text
Agents read branches.
Agents write branches.
Sessions provide shared workspace.
```

Subagents should not "read a session" as if the session were a conversation. They should read a branch. The session gives them locality: files, artifacts, permissions, project metadata, and lifecycle ownership.

## Agent Source

Support both inline and stored sources.

```csharp
public enum SubAgentSourceKind
{
    InlineConfig,
    StoredAgent
}
```

Equivalent API shape:

```csharp
SubAgent.FromConfig(
    name,
    description,
    agentConfig,
    executionPolicy);

SubAgent.FromAgentId(
    name,
    description,
    agentId,
    executionPolicy);
```

Exactly one of `AgentConfig` or `AgentId` should be set.

### Inline Config

Inline config is best for:

- simple code-local subagents;
- tests;
- samples;
- app-defined helper agents;
- fast DX where a separate stored definition is unnecessary.

Example:

```csharp
[SubAgent]
public SubAgent Reviewer()
{
    return SubAgent.FromConfig(
        name: "Reviewer",
        description: "Reviews code for quality and security.",
        agentConfig: new AgentConfig
        {
            Name = "Reviewer",
            SystemInstructions = "Review code for bugs, clarity, and security."
        });
}
```

### Stored Agent

Stored agent references are best for:

- HPD-OS user-created agents;
- durable reusable specialists;
- editable agent definitions;
- stable subagent attribution;
- branch metadata linking;
- multi-client environments;
- administrative lifecycle management.

Example:

```csharp
[SubAgent]
public SubAgent Reviewer()
{
    return SubAgent.FromAgentId(
        name: "Reviewer",
        description: "Reviews code for quality and security.",
        agentId: "code-reviewer");
}
```

The stored agent should be created before invocation through one of these paths:

```text
application startup registration
builder persist-on-build
admin/API/UI creation
```

Subagent invocation should not create the stored definition. It should resolve it.

## Session Policy

Session policy chooses the workspace/container.

```csharp
public enum SubAgentSessionPolicy
{
    ParentSession,
    NewSession,
    SharedSession
}
```

### ParentSession

Use the caller's session.

This should be the default.

It keeps the subagent in the same workspace as the caller:

- same uploaded files;
- same artifacts;
- same permissions;
- same project metadata;
- same branch tree;
- same cleanup/lifecycle.

Default subagents should normally run here.

### NewSession

Create a fresh child session for the invocation.

Use when the subagent should be completely isolated from the caller's workspace.

This is useful for:

- sandboxed tasks;
- tests;
- tasks that must not inherit caller assets or permissions;
- independent one-shot workers whose output is only the returned result.

### SharedSession

Use a stable subagent-owned session across invocations.

This is for persistent specialists with their own memory:

```text
shared session: architect-memory
    branch: main
    branch: call-123
    branch: call-456
```

Use when the specialist should remember prior work independently of the calling session.

This is powerful but risky:

- possible cross-user leakage;
- concurrency conflicts;
- stale context;
- unclear ownership;
- harder cleanup.

Therefore it should be explicit and not the default.

## Branch Policy

Branch policy chooses the context and write target.

```csharp
public enum SubAgentBranchPolicy
{
    ForkFromParentBranch,
    FreshBranch,
    ExistingBranch,
    ParentBranch
}
```

### ForkFromParentBranch

Fork a new branch from the parent branch at the invocation point.

This should be the default.

Behavior:

```text
parent session
    main
        parent messages up to tool call

    subagent/reviewer-abc
        copied context from main up to invocation point
        subagent user prompt
        subagent assistant work
        subagent tool calls/results
```

The subagent sees the parent context and writes to its own branch.

Best for:

- reviewers;
- planners;
- researchers;
- summarizers;
- evaluators;
- background workers that should stay attached to the current workspace.

### FreshBranch

Create a new empty branch in the chosen session.

Behavior:

```text
parent session
    main
    subagent/researcher-abc
        no copied messages
        linked by metadata to parent branch/tool call
```

Best when the subagent needs the same workspace but not the parent conversation history.

This is not equivalent to the current `ForkBranchAsync(..., fromMessageIndex: 0)` behavior except when the source branch is already empty. For a non-empty source branch, index `0` copies the first parent message.

Recommended implementation:

```csharp
await agent.CreateBranchAsync(
    sessionId,
    branchId,
    metadata,
    cancellationToken);
```

This core method can be internal. Application users do not need to call it directly; it exists so generated subagent runtime code and hosting services can create true empty execution branches without abusing fork semantics.

Alternative if branch creation is intentionally folded into the fork API:

```csharp
await agent.ForkBranchAsync(
    sessionId,
    sourceBranchId,
    newBranchId,
    fromMessageIndex: null,
    metadata,
    cancellationToken);
```

Here `null` means "before the first message / copy no messages." Avoid using `-1` as the public API sentinel because it makes an otherwise invalid index valid only by convention. If a named value is preferred, use an explicit fork point model such as:

```csharp
ForkPoint.BeforeFirstMessage
ForkPoint.AfterMessage(index)
```

### ExistingBranch

Reuse a specific existing branch.

Best for stateful specialists or long-running lanes inside a session:

```text
session
    main
    subagent/project-planner
```

This is the branch equivalent of stable specialist memory.

### ParentBranch

Run directly in the caller's branch.

This is the old `PerSession` behavior.

It should remain possible, but only as an explicit opt-in because it mutates the visible parent conversation.

Use when a subagent is intentionally acting as a participant or co-author in the same branch.

## Recommended Default

The default should be:

```text
SubAgentSessionPolicy.ParentSession
SubAgentBranchPolicy.ForkFromParentBranch
```

Meaning:

```text
same workspace, separate execution lane
```

This preserves the strongest benefits:

- parent branch stays clean;
- subagent gets parent context;
- subagent work is durable;
- HPD-OS can show or hide subagent branches;
- branch metadata can link child work to parent tool calls;
- reconnection/hydration can reconstruct both parent and subagent work.

## Proposed API Shape

### Core Types

```csharp
public sealed class SubAgent
{
    public string Name { get; init; } = "";
    public string Description { get; init; } = "";

    public SubAgentSourceKind SourceKind { get; init; }
    public AgentConfig? AgentConfig { get; init; }
    public string? AgentId { get; init; }

    public SubAgentExecutionPolicy ExecutionPolicy { get; init; } = SubAgentExecutionPolicy.Default;

    public Type[] ToolHarnessTypes { get; init; } = [];
    public Dictionary<string, object>? Metadata { get; init; }
}

public sealed record SubAgentExecutionPolicy(
    SubAgentSessionPolicy SessionPolicy,
    SubAgentBranchPolicy BranchPolicy,
    string? SharedSessionId = null,
    string? ExistingBranchId = null,
    string? BranchNamePrefix = null)
{
    public static SubAgentExecutionPolicy Default { get; } =
        new(SubAgentSessionPolicy.ParentSession, SubAgentBranchPolicy.ForkFromParentBranch);
}
```

### Policy Validation

The execution policy should reject ambiguous or impossible combinations early.

Rules:

```text
SharedSessionId
    required when SessionPolicy == SharedSession
    invalid when SessionPolicy == ParentSession or NewSession

ExistingBranchId
    required when BranchPolicy == ExistingBranch
    invalid when BranchPolicy == ForkFromParentBranch, FreshBranch, or ParentBranch

ParentBranch
    requires a parent SessionId and BranchId at invocation time

ForkFromParentBranch
    requires a parent SessionId and BranchId at invocation time

FreshBranch
    requires a resolved session, but does not require a parent branch

NewSession
    creates a child session before resolving the branch policy
```

Factory methods should validate static policy shape. The generated runtime should validate invocation-time requirements, because parent session and branch availability are only known when the subagent tool is called.

### Factory API

```csharp
public sealed class SubAgent
{
    public static SubAgent FromConfig(
        string name,
        string description,
        AgentConfig agentConfig,
        SubAgentExecutionPolicy? executionPolicy = null,
        params Type[] toolharnessTypes);

    public static SubAgent FromAgentId(
        string name,
        string description,
        string agentId,
        SubAgentExecutionPolicy? executionPolicy = null,
        params Type[] toolharnessTypes);
}
```

### Convenience Policies

```csharp
public static class SubAgentExecutionPolicies
{
    public static SubAgentExecutionPolicy ParentSessionForkedBranch();
    public static SubAgentExecutionPolicy ParentSessionFreshBranch();
    public static SubAgentExecutionPolicy ParentBranch();
    public static SubAgentExecutionPolicy NewSession();
    public static SubAgentExecutionPolicy SharedSessionFreshBranch(string sessionId);
    public static SubAgentExecutionPolicy SharedSessionExistingBranch(string sessionId, string branchId);
    public static SubAgentExecutionPolicy ExistingBranch(string branchId);
}
```

```csharp
        description: "Reviews code in an isolated branch.",
        agentId: "code-reviewer");
}
```

This means:

```text
Agent source: stored agent "code-reviewer"
Session: parent session
Branch: fork from parent branch
```

### Example: Inline Local SubAgent


## Generated Runtime Flow

The generated subagent wrapper should perform these steps:

```text
1. Create subagent definition by invoking the [SubAgent] method.
2. Resolve parent execution context.
3. Resolve child agent source.
4. Build child agent.
5. Resolve session policy.
6. Resolve branch policy.
7. Subscribe to child events and bubble them to parent coordinator.
8. Run child agent against resolved session/branch.
9. Return final text/tool result to parent.
```

### Resolve Agent Source

Inline config:

```csharp
var agentBuilder = new AgentBuilder(subAgentDef.AgentConfig!);
```

Stored agent:

```csharp
var parentStore = functionContext?.GetParentAgentStore();
var agentBuilder = new AgentBuilder()
    .WithAgentId(subAgentDef.AgentId!)
    .WithAgentStore(parentStore ?? AgentBuilderDefaults.AgentStore);
```

If parent agent store is not exposed yet, add it to `FunctionExecutionContext`.

Provider inheritance should still apply:

```csharp
if (subAgentDef.SourceKind == SubAgentSourceKind.InlineConfig &&
    subAgentDef.AgentConfig?.Provider == null &&
    parentChatClient != null)
{
    agentBuilder.WithChatClient(parentChatClient);
}
```

Stored-agent subagents should not inherit the parent chat client by default. A stored agent should normally define its own provider, use deferred provider configuration, or opt into parent chat-client inheritance through an explicit future flag.

Inline-config subagents may keep the current convenience behavior:

```text
if inline config has no Provider and parent chat client exists, inherit parent chat client
```

### Resolve Session Policy

`ParentSession`:

```text
require parent SessionId
attach parent session store to child builder
use parent SessionId
```

`NewSession`:

```text
create new child session
metadata links it to parent session/branch/tool call
```

`SharedSession`:

```text
use configured shared session id
create it only if missing
```

### Resolve Branch Policy

`ForkFromParentBranch`:

```text
load parent branch
determine fork point
create subagent branch id
fork parent branch into subagent branch with metadata
run child on subagent branch
```

Initial fork-point rule:

```text
fork from the latest committed parent branch message visible at function invocation time
```

This is intentionally conservative because the current runtime invokes function bodies while the parent turn is still in progress. If a later runtime-owned turn model can identify a durable assistant tool-call message before tool result commit, the fork point can be refined to:

```text
after the parent assistant tool-call message
before the parent tool-result message
```

The important invariant is that the child branch represents the parent context available to the subagent, and the parent branch receives only the eventual tool result, not the child transcript.

`FreshBranch`:

```text
create new empty branch in selected session
persist branch-created event with metadata
run child on new branch
```

If the current store does not expose a direct "create empty branch" API, add one rather than misusing `ForkBranchAsync`.

`FreshBranch` should create a branch with zero copied messages even when the selected session already has non-empty branches.

`ExistingBranch`:

```text
load configured branch
run child there
```

`ParentBranch`:

```text
run child with parent SessionId and parent BranchId
```

## Branch Naming

Subagent branch IDs should be deterministic enough to debug and unique enough to avoid collisions.

Recommended format:

```text
subagent/{normalized-subagent-name}/{short-run-id}
```

Examples:

```text
subagent/reviewer/01JY...
subagent/researcher/01JY...
subagent/planner/01JY...
```

For `ExistingBranch`, caller supplies the branch id.

For `SharedSession`, branch policy decides whether the branch is stable or per-call.

## Metadata Standard

Every subagent-created branch should include standard metadata.

Minimum:

```json
{
  "kind": "subagent",
  "subAgentName": "Reviewer",
  "subAgentAgentId": "code-reviewer",
  "subAgentSourceKind": "StoredAgent",
  "parentAgentId": "main-assistant",
  "parentSessionId": "session-123",
  "parentBranchId": "main",
  "sessionPolicy": "ParentSession",
  "branchPolicy": "ForkFromParentBranch",
  "visibility": "hidden"
}
```

When available, also include:

```json
{
  "parentMessageTurnId": "turn_abc",
  "parentToolCallId": "call_xyz",
  "subAgentRunId": "run_123",
  "createdBy": "subagent",
  "purpose": "review-current-diff"
}
```

This lets HPD-OS:

- hide subagent branches by default;
- show expandable subagent work;
- group subagent branches under a parent turn;
- clean up child branches with their parent session;
- render a subagent trace;
- compare subagent outputs;
- hydrate subagent execution after reconnect.

## Event Persistence

Subagent work should persist to the branch it runs on.

For the default policy:

```text
parent branch
    parent user message
    parent assistant tool call
    subagent tool result summary
    parent assistant final answer

subagent branch
    copied context up to fork point
    subagent input
    subagent assistant deltas
    subagent tool calls/results
    subagent final answer
```

The parent branch should not receive every subagent internal event as durable parent-branch history.

Live observers may still see bubbled subagent events, but persisted branch history should preserve ownership:

```text
parent events persist to parent branch
subagent events persist to subagent branch
```

If HPD-OS wants to show subagent activity inline, it should do so by following metadata links, not by requiring child events to be duplicated into the parent branch.

## Relationship To Runtime-Owned Runs

This proposal composes with runtime-owned runs.

Subagent invocation still occurs as part of an agent turn, but the child agent should run against its selected session/branch. If runtime-owned execution is active, child work may eventually become independently queued work.

The important invariant is the same:

```text
runtime owns execution
branch owns persisted history
stream observes events
explicit cancellation cancels work
```

For default branch-native subagents:

```text
parent runtime turn
    invokes subagent tool
        child agent writes to subagent branch
        child events bubble live
        child final result returns as tool result
    parent continues
```

Future background subagents can use the same branch metadata and run independently.

## Cancellation Semantics

Initial behavior:

```text
parent turn cancellation cancels active subagent invocation
```

This matches current tool-call semantics.

Future behavior may allow detached/background subagents:

```text
parent turn starts background subagent branch run
parent receives accepted/pending result
subagent continues independently
explicit cancellation targets subagent run id
```

That should be a later extension, not part of the first semantic cleanup.

## Concurrency

The current `SharedSession` warning is valid. Reusing one session/branch concurrently can cause conflicts.

Recommended v1 policy:

- default forked subagent branches are safe because each invocation creates a distinct branch;
- `ParentBranch` follows the parent turn's normal serialization;
- `ExistingBranch` must reject concurrent runs on the same branch unless branch run queuing exists;
- `SharedSession + ExistingBranch` should reject concurrent runs by default;
- `SharedSession + FreshBranch` or `SharedSession + ForkFromInputSnapshot` can be allowed because each call has a distinct branch.

Branch run locking should be branch-based, not stream-based. Generated subagent wrappers should participate in the same target-branch run locking rules as hosted branch execution rather than bypassing them with direct `RunAsync` calls on reused branches.

## Breaking Changes

This should intentionally break the old subagent semantics.

Remove or replace:

```csharp
SubAgentSessionMode
SubAgentFactory
CreatePerSession(...)
CreateStateful(...)
SessionMode
SharedSessionId
SharedBranchId
```

Recommended replacements:

```csharp
SubAgentSessionPolicy
SubAgentBranchPolicy
SubAgentExecutionPolicy
SubAgent.FromConfig(...)
SubAgent.FromAgentId(...)
SubAgentExecutionPolicies.SharedSessionFreshBranch(...)
SubAgentExecutionPolicies.SharedSessionExistingBranch(...)
SubAgentExecutionPolicies.ParentBranch()
```

`ParentBranch` replaces old `PerSession` behavior.

Shared-session subagents remain available, but the helper must explicitly choose whether each call gets a fresh branch or reuses an existing branch.

`Stateless` becomes one of these explicit policies:

```text
NewSession + FreshBranch
ParentSession + FreshBranch
```

The old word "stateless" is not precise enough because it does not say which workspace owns the run.

## Migration Mapping

Old:

```text
Create(...)
SessionMode = Stateless
```

New likely equivalent:

```text
FromConfig(...)
NewSession + FreshBranch
```

But the recommended new default for most subagents is:

```text
FromConfig(...)
ParentSession + ForkFromParentBranch
```

Old:

```text
CreateStateful(...)
SharedSessionId
SharedBranchId
```

New:

```text
FromConfig(...)
SharedSessionExistingBranch(sessionId, branchId)
```

Old:

```text
CreatePerSession(...)
```

New semantic replacement:

```text
ParentSession + ForkFromParentBranch
```

Old behavior-preserving replacement:

```text
ParentSession + ParentBranch
```

The behavior-preserving replacement should not be the default.

## Implementation Plan

### Required Runtime Primitives

Before the source generator rewrite can be complete, the runtime needs a few explicit primitives:

- parent agent store access from `FunctionExecutionContext`;
- internal empty branch creation for `FreshBranch`;
- deterministic subagent branch id and run id generation;
- branch metadata helper for standard subagent metadata;
- fork-point selection from the parent invocation context;
- branch target/run locking for policies that reuse an existing branch;
- structured result metadata for child session id, branch id, and run id.

These are runtime concerns, not user-facing API requirements. Application authors should choose policies; the generated wrapper should handle the branch/run mechanics.

### Phase 1: Model Types

Add:

- `SubAgentSourceKind`;
- `SubAgentSessionPolicy`;
- `SubAgentBranchPolicy`;
- `SubAgentExecutionPolicy`;
- factory methods for `FromConfig` and `FromAgentId`;
- validation that exactly one source is provided.

Keep old APIs only if needed temporarily, marked obsolete and implemented in terms of the new policies.

Because compatibility is not required, direct removal is acceptable.

### Phase 2: Agent Store Access

Expose parent agent store to generated subagent wrappers.

Options:

1. Add `GetParentAgentStore()` to `FunctionExecutionContext`.
2. Add agent store to `AgentContext`/`HookContext`.
3. Use a configured default store for stored-agent subagents.

Preferred:

```text
FunctionExecutionContext exposes parent agent store.
```

That keeps generated wrappers explicit and testable.

### Phase 3: Source Generator Rewrite

Update `SubAgentCapability.GenerateRegistrationCode` to:

- resolve inline config or stored agent id;
- attach parent session store when needed;
- attach parent agent store when needed;
- resolve session policy;
- resolve branch policy;
- create/fork branches with metadata;
- run child on resolved branch;
- return final result.

Replace generated `SessionMode` metadata with:

```text
SubAgentSourceKind
SubAgentSessionPolicy
SubAgentBranchPolicy
```

### Phase 4: Branch Creation API

Ensure the core agent/session store supports:

- fork branch with metadata;
- create empty branch with metadata;
- list/load subagent branches by metadata.

If no direct empty branch creation API exists, add one.

Do not fake `FreshBranch` by forking from an unrelated branch. The current fork API can produce an empty branch only when the source branch itself is empty. For non-empty source branches, `fromMessageIndex: 0` copies the first message.

Preferred v1 shape:

```csharp
internal Task<string> CreateBranchAsync(
    string sessionId,
    string branchId,
    Dictionary<string, object>? metadata = null,
    CancellationToken cancellationToken = default);
```

This should be a framework/runtime primitive, not necessarily part of the public `Agent` API. User-facing branch creation can remain in hosting/services, while generated subagent wrappers use the internal primitive.

If the framework chooses to support "before first message" through forking instead, prefer a nullable or named fork point rather than a magic `-1` index:

```csharp
internal Task<string> ForkBranchAsync(
    string sessionId,
    string sourceBranchId,
    string newBranchId,
    int? fromMessageIndex,
    Dictionary<string, object>? metadata = null,
    CancellationToken cancellationToken = default);
```

Rules:

```text
fromMessageIndex == null
    copy no messages
    optionally copy no branch-scoped middleware state unless explicitly requested

fromMessageIndex >= 0
    copy messages 0..fromMessageIndex
    copy branch-scoped middleware state

fromMessageIndex < 0
    invalid
```

### Phase 5: Event And Persistence Rules

Ensure child events persist to the child branch.

Ensure parent branch receives the subagent result as the tool result, not the full child transcript.

Live event bubbling can remain, but event scopes must be correct.

### Result Metadata

The parent LLM may receive only the subagent's final text as the tool result, but the runtime should retain structured result metadata for HPD-OS linking and replay.

Minimum metadata:

```json
{
  "status": "completed",
  "branchId": "subagent/reviewer/01JY...",
  "sessionId": "session-123",
  "subAgentName": "Reviewer",
  "subAgentRunId": "run_123"
}
```

If the subagent fails:

```json
{
  "status": "failed",
  "branchId": "subagent/reviewer/01JY...",
  "sessionId": "session-123",
  "subAgentName": "Reviewer",
  "subAgentRunId": "run_123",
  "errorType": "OperationCanceledException"
}
```

This can be stored through `FunctionExecutionContext.ResultMetadata` so the parent branch can persist a compact tool result while HPD-OS can still follow the metadata link to the child branch.

### Phase 6: Tests

Add tests for:

- `FromConfig` builds child from inline config;
- `FromAgentId` resolves child from `IAgentStore`;
- invalid execution policy combinations throw during factory validation;
- default policy is `ParentSession + ForkFromParentBranch`;
- default subagent does not append messages to parent branch;
- default subagent creates a child branch with metadata;
- default fork point uses the latest committed parent branch message visible at invocation time;
- child branch contains subagent messages/tool events;
- parent branch contains tool call/result but not full child transcript;
- `ParentBranch` explicitly preserves old write-into-parent behavior;
- `FreshBranch` creates an empty child branch in parent session from a non-empty parent session;
- `FreshBranch` does not copy parent branch messages;
- `FreshBranch` does not copy branch-scoped middleware state by default;
- `NewSession` creates a child session and branch;
- `SharedSession` reuses stable session/branch;
- stored-agent subagents do not inherit the parent chat client unless explicitly configured;
- inline-config subagents still inherit parent chat client when provider is null;
- result metadata includes child session id, branch id, subagent name, and run id;

Remove or rewrite tests that document current `PerSession` parent-branch appending.

## HPD-OS Implications

HPD-OS can treat branches by metadata kind.

Normal branches:

```json
{ "kind": "conversation" }
```

Subagent branches:

```json
{ "kind": "subagent", "visibility": "hidden" }
```

UI behavior:

- hide subagent branches in normal branch navigation by default;
- show subagent branch under the parent tool call;
- allow opening the subagent branch for inspection;
- hydrate subagent branch events independently;
- preserve parent branch readability.

This turns subagents into inspectable workspaces instead of invisible tool calls or parent-branch pollution.

## Related Future Work

The branch-native subagent model exposes several adjacent features that should be documented now but not included in the first implementation. They are related because subagent branches make them useful, but each needs its own design pass.

### 1. Reduced And Compacted Forks

Current branch forking copies parent messages up to the fork point.

That is correct for a faithful branch:

```text
parent branch messages 0..N
    -> fork branch messages 0..N
```

For subagents, this may not always be the right tradeoff. A reviewer, planner, or researcher often needs enough context to work, but not necessarily every raw historical message.

Future fork context policies should be considered:

```text
Full
    copy parent messages up to fork point

Reduced
    create a summary/checkpoint plus recent messages

LastN
    copy only the most recent N messages

Compacted
    replace old persisted content with a summary checkpoint
```

This connects to the existing `CompactionMiddleware`, but it is not the same feature.

Current compaction is soft reduction:

```text
full branch history remains persisted
summary is stored in middleware state
model-visible ConversationHistory is reduced during a turn
```

Compacted forks would be a branch/store feature:

```text
new branch starts from compacted durable history
raw copied history may not exist in the child branch
branch metadata records the compaction policy
```

Hard compaction is a stronger form:

```text
old persisted branch content is replaced, deleted, or tombstoned after summary
```

That should not be hidden inside ordinary compaction middleware because it changes retention and audit semantics. It needs explicit user/application intent.

Open questions:

- Should hard compaction rewrite branch event documents, append tombstone events, or create a new compacted branch?
- How should HPD-OS show that old raw content was summarized or removed?
- Should compaction require a user-visible confirmation or policy flag?
- Can summaries be trusted as the only durable representation for some sessions?
- How does compaction interact with branch hydration and sibling navigation?

This is future work, but the subagent branch model should leave room for:

```csharp
ForkFromParentBranch(context: Full | Reduced | LastN | Compacted)
```

### 2. Asynchronous Subagent Runs

Initial branch-native subagents can remain synchronous:

```text
parent calls subagent tool
subagent runs on child branch
subagent returns final result
parent continues
```

The runtime already has infrastructure that points toward asynchronous agent work:

- `FunctionExecutionContext.RegisterBackgroundTask(...)`;
- runtime-owned background task registration;
- runtime cancellation token;
- background task lifecycle events;
- function invocation snapshots;
- event coordinator access from background work.

That means a future subagent tool could start work and return immediately:

```text
parent calls subagent tool
tool creates subagent branch
tool registers background agent work
tool returns { status: "started", branchId, taskId, runId }
subagent continues on its branch
HPD-OS observes branch events
```

This is valuable for:

- long-running research;
- code review;
- indexing;
- evaluation;
- parallel specialist work;
- jobs that should survive UI refresh/reconnect.

Open questions:

- Does background subagent work run through the same `Agent` runtime inbox or through a branch run service?
- What is the durable run id model for background subagents?
- How does explicit cancellation target a background subagent run?
- Should background subagent results eventually post a summary back to the parent branch?
- Should parent agents be able to wait for a background subagent later?

This is not required for v1. The first implementation should make synchronous branch-native subagents correct, while preserving the branch/run metadata needed for asynchronous work later.

### 3. Invocation Mode DX

Once synchronous and asynchronous subagent runs both exist, the framework needs a clear DX for choosing between them.

The decision should not be hidden in implementation details. It should be part of the subagent execution policy.

Possible extension to the existing policy shape:

```csharp
public enum SubAgentInvocationMode
{
    Synchronous,
    Background
}

// Add to SubAgentExecutionPolicy when background invocation is introduced.
SubAgentInvocationMode InvocationMode = SubAgentInvocationMode.Synchronous;
```

Default:

```text
ParentSession + ForkFromParentBranch + Synchronous
```

Long-running specialist:

```text
ParentSession + ForkFromParentBranch + Background
```

Synchronous result shape:

```json
{
  "status": "completed",
  "branchId": "subagent/reviewer/abc",
  "result": "Found 3 issues..."
}
```

Background result shape:

```json
{
  "status": "started",
  "branchId": "subagent/reviewer/abc",
  "taskId": "task_123",
  "runId": "run_456"
}
```

Open questions:

- Is invocation mode fixed on the subagent definition, overridden by `AgentRunConfig`, or both?
- Should the LLM ever choose synchronous vs background, or should the application choose?
- How should tool descriptions communicate that a background subagent returns a handle instead of a final answer?
- Should background invocation require explicit permission because it creates durable work?

Recommended direction:

```text
subagent definition declares the default invocation mode
application/run config may override it
LLM does not casually choose mode unless the tool schema is explicit
```

This keeps the framework flexible without making behavior unpredictable.

## Non-Goals

This proposal does not require:

- background/detached subagent execution in v1;
- a new run database;
- preserving old `CreatePerSession` behavior as the default;
- duplicating all child events into the parent branch;
- forcing all subagents to use stored agent ids;
- removing inline config convenience;
- making shared-session subagents safe for all concurrent use cases.

## Success Criteria

This refactor is successful when:

- subagent API names no longer imply that sessions are conversation threads;
- default subagents run in the parent session but write to a distinct branch;
- parent branches are not polluted by subagent transcripts unless `ParentBranch` is explicitly selected;
- subagent-created branches include standard metadata;
- stored-agent subagents can resolve by `AgentId`;
- inline-config subagents still work for simple code-local DX;
- HPD-OS can discover and inspect subagent branches;
- branch hydration reconstructs subagent work;
- old `PerSession` behavior is no longer accidental.

## Recommendation

Proceed with the breaking change.

The current infrastructure already has most of what is needed:

- stored agent identities;
- agent store;
- parent function execution context;
- session store access;
- branch metadata;
- branch forking;
- event persistence.

The required change is mostly semantic: stop treating subagent execution as a session mode and make it an explicit agent-source plus session-policy plus branch-policy decision.

The new default should be:

```text
ParentSession + ForkFromParentBranch
```

That is the right model for HPD-Agent after the session/branch split.
