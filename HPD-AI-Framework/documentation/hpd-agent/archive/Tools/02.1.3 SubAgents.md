# SubAgents

SubAgents are child agents exposed as tools. A parent agent can delegate a complex task to a SubAgent, let that child agent reason, call its own tools, and return a clean result to the parent.

Use a SubAgent when the task needs autonomous reasoning, a specialized prompt, a different model, or a separate tool set. If the steps are known upfront, use a [Skill](02.1.2%20Skills.md). If the task is one deterministic operation, use an [AIFunction](02.1.1%20AIFunctions.md).

## The Mental Model

HPD-Agent treats sessions and branches separately:

```text
Session = shared workspace/container
Branch  = conversation and execution history
```

By default, a SubAgent runs in the parent's session and creates its own branch forked from the parent's current branch:

```text
parent session
  main
    parent messages
    parent tool call to CodeReviewer
    parent receives final subagent result

  subagent/code-reviewer/abc123
    copied parent context up to the call
    child user prompt
    child assistant work
    child tool calls/results
    child final answer
```

This keeps the parent branch readable while making the SubAgent's full work durable, inspectable, and replayable.

## Basic Usage

Create a harness method, mark it with `[SubAgent]`, and return a `SubAgent`.

```csharp
using HPD.Agent;

public partial class ReviewHarness
{
    [SubAgent]
    public SubAgent CodeReviewer()
    {
        return SubAgent.FromConfig(
            name: "CodeReviewer",
            description: "Reviews code for bugs, clarity, and security.",
            agentConfig: new AgentConfig
            {
                Name = "Code Reviewer",
                SystemInstructions = """
                    You are an expert C# code reviewer.

                    Review the code for:
                    1. correctness bugs
                    2. security issues
                    3. maintainability problems
                    4. missing tests

                    Return concise findings with severity and suggested fixes.
                    """
            },
            typeof(FileSystemTools));
    }
}
```

Register the harness on the parent agent:

```csharp
var agent = await new AgentBuilder()
    .WithProvider("openai", "gpt-4o")
    .WithSessionStore("./sessions")
    .WithHarness<ReviewHarness>()
    .BuildAsync();

var sessionId = await agent.CreateSessionAsync();

await agent.RunAsync(
    "Review the current diff.",
    sessionId: sessionId,
    branchId: "main");
```

The default SubAgent execution policy is:

```text
ParentSession + ForkFromParentBranch
```

That means the child sees the parent branch context, writes its own work to a child branch, and returns only the result to the parent branch.

## Agent Source

A SubAgent can be created from an inline config or from a stored agent id.

### Inline Config

Inline config is best for code-local helper agents, tests, samples, and simple app-defined specialists.

```csharp
[SubAgent]
public SubAgent Summarizer()
{
    return SubAgent.FromConfig(
        name: "Summarizer",
        description: "Summarizes the current conversation branch.",
        agentConfig: new AgentConfig
        {
            Name = "Summarizer",
            SystemInstructions = "Summarize the conversation clearly and briefly."
        });
}
```

Inline SubAgents inherit the parent chat client when `AgentConfig.Provider` is not set. This is convenient when the SubAgent should use the same provider/model as the parent.

### Stored Agent

Stored-agent SubAgents reference an agent definition by id. This is best for reusable user-created agents, app-editable specialists, administrative lifecycle management, and stable attribution.

```csharp
[SubAgent]
public SubAgent SecurityAuditor()
{
    return SubAgent.FromAgentId(
        name: "SecurityAuditor",
        description: "Audits code for security vulnerabilities.",
        agentId: "security-auditor");
}
```

The parent agent must have an agent store so the generated wrapper can resolve the stored definition:

```csharp
var agentStore = new JsonAgentStore("./agents");

await agentStore.SaveAsync(new StoredAgent
{
    Id = "security-auditor",
    Name = "Security Auditor",
    Config = new AgentConfig
    {
        Name = "Security Auditor",
        SystemInstructions = "Audit code for vulnerabilities and rank findings by severity.",
        Provider = new ProviderConfig
        {
            ProviderKey = "openai",
            ModelName = "gpt-4o"
        }
    }
});

var parent = await new AgentBuilder()
    .WithProvider("openai", "gpt-4o")
    .WithSessionStore("./sessions")
    .WithAgentStore(agentStore)
    .WithHarness<ReviewHarness>()
    .BuildAsync();
```

Stored agents should normally define their own provider or provider configuration. Unlike inline configs, stored-agent SubAgents do not implicitly inherit the parent chat client.

## Execution Policies

`SubAgentExecutionPolicy` answers two questions:

```text
1. Which session/workspace owns the run?
2. Which branch receives the child agent's work?
```

For forked-branch SubAgents, the policy can also answer whether the new child branch
should be compacted when it is created.

Most users should use the helper methods on `SubAgentExecutionPolicies`.

| Helper | Session | Branch | Use When |
|---|---|---|---|
| `ParentSessionForkedBranch()` | Parent session | New branch forked from parent branch | Default. The child needs parent context but should keep its work separate. |
| `ParentSessionFreshBranch()` | Parent session | New empty branch | The child needs the same workspace/assets but not the parent conversation history. |
| `ParentBranch()` | Parent session | Parent branch | The child should intentionally write directly into the visible parent branch. |
| `NewSession()` | New child session | New empty branch | The child should be isolated from the parent workspace. |
| `ExistingBranch(branchId)` | Parent session | Existing branch | The child should continue a stable lane inside the parent session. |
| `SharedSessionFreshBranch(sessionId)` | Shared session | New empty branch per call | The specialist has its own workspace, but each invocation gets a separate branch. |
| `SharedSessionExistingBranch(sessionId, branchId)` | Shared session | Existing branch | The specialist has persistent memory in one stable branch. |

### Default: Parent Session, Forked Branch

```csharp
[SubAgent]
public SubAgent Planner()
{
    return SubAgent.FromConfig(
        name: "Planner",
        description: "Creates an implementation plan using the current conversation context.",
        agentConfig: plannerConfig);
}
```

Equivalent explicit form:

```csharp
return SubAgent.FromConfig(
    name: "Planner",
    description: "Creates an implementation plan using the current conversation context.",
    agentConfig: plannerConfig,
    executionPolicy: SubAgentExecutionPolicies.ParentSessionForkedBranch());
```

### Compact The SubAgent Fork

Forked SubAgents can compact their child branch before it is persisted.

```csharp
[SubAgent]
public SubAgent Researcher()
{
    return SubAgent.FromConfig(
        name: "Researcher",
        description: "Researches a topic using current conversation context.",
        agentConfig: researcherConfig,
        executionPolicy: SubAgentExecutionPolicies.ParentSessionForkedBranch(
            branchCompaction: SubAgentBranchCompaction.Enabled));
}
```

This is useful when the parent conversation is long but the child agent only needs a
compact handoff plus recent context. The source parent branch is not changed. Only the
new SubAgent branch is compacted.

The available values are:

| Value | Behavior |
|---|---|
| `Inherit` | Default. Use the parent agent's `CompactionConfig.CompactOnFork` setting. |
| `Enabled` | Compact this SubAgent fork even if global `CompactOnFork` is `false`. |
| `Disabled` | Do not compact this SubAgent fork even if global `CompactOnFork` is `true`. |

SubAgent fork compaction still uses the agent's configured `CompactionMiddleware`.
That means the selected compaction strategy, summary style, retention policy, and
boundaries come from `WithCompaction(...)`; the SubAgent policy only chooses whether
fork-time compaction should run for this SubAgent.

```csharp
var agent = new AgentBuilder()
    .WithProvider("openai", "gpt-4o")
    .WithSessionStore("./sessions")
    .WithCompaction(compaction =>
    {
        compaction.Enabled = true;
        compaction.CompactOnFork = false;
        compaction.Strategy = new SummarizingCompactionOptions
        {
            TargetRecentMessageCount = 24,
            SummaryStyle = SummaryStyle.Handoff
        };
    })
    .WithHarness<ResearchHarness>()
    .Build();
```

With this setup, ordinary forks are not compacted by default, but `Researcher` can opt
in with `SubAgentBranchCompaction.Enabled`.

`BranchCompaction` is only valid with `ForkFromParentBranch`, because that is the only
SubAgent branch policy that copies parent history. Fresh, existing, and parent-branch
policies do not create a fork to compact.

### Same Workspace, No Parent Conversation

```csharp
[SubAgent]
public SubAgent AssetIndexer()
{
    return SubAgent.FromConfig(
        name: "AssetIndexer",
        description: "Indexes uploaded files without reading the parent conversation.",
        agentConfig: indexerConfig,
        executionPolicy: SubAgentExecutionPolicies.ParentSessionFreshBranch());
}
```

### Write Into The Parent Branch

Use `ParentBranch()` only when the SubAgent is meant to participate directly in the parent conversation history.

```csharp
[SubAgent]
public SubAgent CoAuthor()
{
    return SubAgent.FromAgentId(
        name: "CoAuthor",
        description: "Writes directly in the current branch.",
        agentId: "co-author",
        executionPolicy: SubAgentExecutionPolicies.ParentBranch());
}
```

### Persistent Specialist Memory

Use a shared session plus an existing branch when the specialist should keep memory across invocations independently of the caller.

```csharp
[SubAgent]
public SubAgent Architect()
{
    return SubAgent.FromAgentId(
        name: "Architect",
        description: "Maintains long-running architecture memory.",
        agentId: "architect",
        executionPolicy: SubAgentExecutionPolicies.SharedSessionExistingBranch(
            sessionId: "architect-memory",
            branchId: "main"));
}
```

Shared persistent branches are powerful but should be used deliberately. They can create cross-user leakage, concurrency conflicts, and stale context if the application does not scope them carefully.

## Optional Branch Metadata

SubAgent-created branches automatically receive metadata such as:

```json
{
  "kind": "subagent",
  "subAgentName": "CodeReviewer",
  "subAgentSourceKind": "InlineConfig",
  "parentSessionId": "session-123",
  "parentBranchId": "main",
  "parentToolCallId": "call-456",
  "subAgentRunId": "run-789",
  "sessionPolicy": "ParentSession",
  "branchPolicy": "ForkFromParentBranch",
  "visibility": "hidden",
  "createdBy": "subagent"
}
```

You can add your own defaults:

```csharp
return SubAgent.FromConfig(
    name: "CodeReviewer",
    description: "Reviews code for quality and security.",
    agentConfig: reviewerConfig,
    executionPolicy: SubAgentExecutionPolicy.Default,
    metadata: new Dictionary<string, object>
    {
        ["purpose"] = "review-current-diff",
        ["visibility"] = "visible"
    },
    harnessTypes: new[] { typeof(FileSystemTools) });
```

This metadata belongs to the branch. Host apps and clients can use it to group SubAgent work under the parent tool call, hide or show SubAgent branches, and hydrate the child branch later.

## Events And Streaming

SubAgent events are live-bubbled to the parent event stream, but durable history stays on the branch that produced it.

```text
Live stream:
  parent events
  child SubAgent events
  parent continuation events

Durable parent branch:
  parent user message
  parent tool call
  SubAgent tool result
  parent final answer

Durable child branch:
  child input
  child assistant deltas/messages
  child tool calls/results
  child final answer
```

Use `AgentEvent.Metadata` to identify live event ownership:

```csharp
agent.On<TextDeltaEvent>(evt =>
{
    var meta = evt.Metadata;

    if (meta?.IsSubAgent == true)
    {
        Console.Write($"[{meta.AgentName}] {evt.Text}");
    }
    else
    {
        Console.Write(evt.Text);
    }

    return ValueTask.CompletedTask;
});
```

For persisted branch relationships, use `Branch.Metadata` or branch events with `branchMetadata`. Do not treat live `AgentEvent.Metadata` as branch metadata.

## Tools And Harnesses

SubAgents only get the harnesses you give them.

```csharp
[SubAgent]
public SubAgent FileAnalyzer()
{
    return SubAgent.FromConfig(
        name: "FileAnalyzer",
        description: "Analyzes files for patterns and issues.",
        agentConfig: new AgentConfig
        {
            Name = "File Analyzer",
            SystemInstructions = "Analyze files and return specific findings."
        },
        typeof(FileSystemTools),
        typeof(SearchTools));
}
```

Give SubAgents the smallest useful tool set. This keeps behavior predictable and reduces permission risk.

## Requirements And Gotchas

- Branch-native policies require a session store. Configure one with `WithSessionStore(...)`.
- `ParentSession`, `ParentBranch`, and `ForkFromParentBranch` require the parent run to have a `SessionId`.
- `ForkFromParentBranch` also requires a parent `BranchId`.
- `SharedSessionExistingBranch(...)` requires that the target branch exists.
- Inline-config SubAgents can inherit the parent chat client when `Provider` is null.
- Stored-agent SubAgents resolve through `IAgentStore` and should normally carry their own provider configuration.
- SubAgents make their own LLM calls, so cost and latency are closer to running another agent than calling a normal function.
- `BranchCompaction` only applies to `ForkFromParentBranch` SubAgents.
- SubAgent fork compaction requires the agent to have compaction middleware configured with a strategy; the SubAgent policy chooses fork behavior, not the strategy itself.
- SubAgents require permission by default because they can perform multiple autonomous actions.

## SubAgents vs Other Tool Types

| Aspect | AIFunction | Skill | SubAgent |
|---|---|---|---|
| Shape | One operation | Guided workflow | Autonomous child agent |
| LLM calls | Parent call only | Parent call only | Child agent calls |
| Tools | Function body | Parent-visible referenced tools | Own harness set |
| History | Parent branch | Parent branch | Separate branch by default |
| Provider | Parent | Parent | Inline inherit or stored/configured |
| Best for | Deterministic work | Known steps | Unknown path or specialized reasoning |

## Best Practices

1. Use the default policy for most delegation: parent workspace, forked child branch.
2. Keep SubAgent instructions narrow and concrete.
3. Give the child only the harnesses it needs.
4. Use stored agents for user-editable or reusable specialists.
5. Use shared-session existing branches only when you really want persistent specialist memory.
6. Use `SubAgentBranchCompaction.Enabled` for context-heavy specialists that benefit from a compact handoff.
7. Use branch metadata for durable relationships and `AgentEvent.Metadata` for live event ownership.
